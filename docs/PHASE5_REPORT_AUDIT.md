## Audit findings

ReportsController routes all reports through ReportingService.ExecuteAsync and reuses CsvWriter for JSON projections. Export loops pages of 200 with a 100,000-row cap. ReportQuery uses explicit UTC half-open ranges, page size 1–200 and max 366 days. Purchase/quotation/order/transfer document dates use Pakistan business dates. Inventory position is current; its valuation is not an historical snapshot.

Existing report filters are inconsistent: only daily sales uses SaleType; many methods accept branch/range only and ignore product/godown/status filters. Transfer and stock-count queries have the most complete scope. GodownId supplied to godown-stock is ignored unless passed as Option. No category/manufacturer/customer/supplier/user/price-level query fields exist. Large dimension reports return unbounded arrays; detail reports are paged.

Sales allocation cost snapshots are the historical profit source. ProductSales starts from sold products and misses return-only products. Trend starts from sale dates and misses return-only dates and groups UTC dates instead of Pakistan business dates. Customer profit does not subtract returns. Retail/wholesale and price-level analysis return zero returns. Below-cost report uses selling rate before allocated discount. Dashboard expense total sums one page, and inventory counts materialize all product rows.

Privacy is incomplete: cost redaction handles some typed DTOs only, misses batch stocks, purchase rows, transfer detail/discrepancies and stock-count variance. Overview trend contains gross profit regardless of profit grants. ReportsView alone exposes financial balances and expense totals. Phase 5 must omit restricted fields or reject restricted reports in the backend, including exports.

Permissions available: reports.view, reports.sales, reports.purchases, reports.inventory, reports.financial, reports.profitability, reports.export and sales.cost_view. Reuse these seeded grants rather than duplicating permission vocabulary. Owner/Manager may select all branches; other users are limited to their branch. Existing godown grants need explicit enforcement.

## Existing finance/reporting reuse

Accounts dashboard uses existing Trial Balance, P&L, Balance Sheet and AR/AP aging endpoints; it is already a financial overview. AccountingController also exposes GL, cash/bank/day books, cash flow, AR/AP/inventory/cash-bank control reconciliation. BudgetsController provides budget-vs-actual. These services are the financial MIS source; do not rebuild journal arithmetic. Customer/supplier operational statement/payment endpoints are drilldown targets, not new ledgers. Main Dashboard is a welcome/identity page; Reports Overview is the existing operational KPI dashboard.

Flutter Reports exposes the inventory above with basic date presets and branch selector; tables are generic and have no document drilldown or paging controls. CSV downloads use the same report path and filters. The project has no chart dependency. Assess one chart library before adding charts.

## Classification limits

COA has AccountType and cash-flow classification, but no explicit current/non-current classification. Report mapped working-capital components only, label incomplete classification, and do not claim a current ratio. Cash conversion cycle requires comparable historical averages and credit-only turnover; defer until source semantics can be validated. Inventory aging is age since earliest opening/purchase movement for the remaining batch, with received/created fallback explicitly identified; it is not FIFO receipt-layer aging.
