# Permission Matrix

This is the authoritative map of which seeded role holds which permission. It was generated by querying the real `RolePermissions`/`Roles`/`Permissions` tables of a fully-migrated database (`pharmacy_test`), not by reading migration source — so it reflects what the application actually enforces today, including every seed migration through Phase 6. Regenerate it after any future permission change with:

```sql
SELECT r."Name", p."Category", p."Code", p."Description"
FROM "RolePermissions" rp
JOIN "Roles" r ON r."Id" = rp."RoleId"
JOIN "Permissions" p ON p."Id" = rp."PermissionId"
ORDER BY p."Category", p."Code", r."Name";
```

Backend authorization is authoritative: every controller action is gated by a `[HasPermission("code")]` policy (or, for the handful of endpoints whose real requirement can't be expressed as a single permission — see below — a bare `[Authorize]` plus an equivalent in-service check) checked against the JWT's `permission` claims, resolved server-side from these exact role grants at login. The Flutter client also hides UI it can't use, but that is convenience only; removing a button client-side is not a security control here, and every write path was confirmed to re-validate independently on the server.

Seeded roles: **Owner**, **Manager**, **Accountant**, **PurchaseManager**, **Pharmacist**, **Cashier**, **StoreKeeper**. There are 179 distinct permission codes; Owner holds all 179.

## Design notes and confirmed-safe findings

- **Owner-only, by design**: `roles.manage`, `users.manage_owner`, `system.backup`, `system.settings.manage`, `recycle_bin.restore`, `branches.manage`, `audit.export`. No other role can touch role/permission assignments, back up or restore infrastructure, change system settings, permanently purge data, or export the audit trail.
- **Owner and Manager are both treated as multi-branch/HQ roles** — every operational service resolves cross-branch data access from role name (`Owner`/`Manager`) or the `branches.view` permission, not from `branches.manage`. If "Manager" is intended to mean a single-branch manager rather than an HQ-level role in this deployment, that is a product decision to revisit — it is consistent everywhere today, not a bug.
- **Cashier confirmed clean of financial-posting power**: no `accounts.journal.post`, `accounts.voucher.post`, `accounts.periods.*`, or `sales.cost_view`. Cashier does hold `accounts.view` and `finance.ledger.view` (branch-scoped read access to financial account balances/ledger) and a full `quotations.*`/`sales_orders.*`/`sales.wholesale` set — plausible for a front-counter role handling more than plain POS, but worth confirming against your actual staffing model before go-live.
- **StoreKeeper holds `godowns.manage`** (assign/unassign other users' godown access and default godown), scoped to their own branch by the service layer. This hands a warehouse-operations role an access-control capability normally reserved for management; kept as-is since it is branch-scoped and was judged a plausible operational need, but confirm intent.
- **PurchaseManager holds `reports.purchases` but not `sales.cost_view`/`reports.profitability`**, so most purchase report detail (which requires cost visibility) will still reject them despite holding the category permission — a functional inconsistency worth a product decision, not a security gap (it fails closed).
- **Branch/godown isolation is enforced by every service independently of these role checks** — a client-supplied `branchId`/`godownId` is validated against the actor's own assignment (via `UserGodowns`) unless the actor qualifies as multi-branch (Owner/Manager/`branches.view`). This was verified by direct code review of every operational service (Sales, Purchasing, Inventory, Stock Transfers, Customers, Suppliers, Quotations, Sales Orders, Accounting) during this hardening pass — see the Phase 7 completion report for the two Medium-severity gaps found and left for a product decision (`PricingService` price levels, since fixed in this pass, and a `CanSelectBranch` permission-coupling landmine, also fixed).
- **Cost/profit/financial redaction is enforced server-side on every report**, independent of role, via a JSON field-stripping pass keyed on `sales.cost_view` / `reports.profitability` / `reports.financial` — confirmed for all typed report DTOs including batch stocks, purchase rows, transfer detail/discrepancies, stock-count variance, and (fixed in this hardening pass) staff cash-variance performance figures.
